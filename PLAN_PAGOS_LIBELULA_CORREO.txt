1. DECISIÓN DE DISEÑO: qué canal de Libélula usar
-------------------------------------------------------------------
Libélula (grupo Todotix) expone el flujo "REGISTRAR DEUDA":
  POST https://api.libelula.bo/rest/deuda/registrar
que devuelve una url_pasarela_pagos a la que se redirige al cliente.
Libélula soporta Cybersource (tarjetas), SimpleQR (BCP/BNB), Botón
BCP, Tigo Money, BNBNet, Pago Express — todos por el mismo servicio,
sin cambios de integración.

Se mantiene el pago manual con comprobante como fallback/alternativa
(pago en efectivo/transferencia con revisión de Admin), y se agrega
Libélula como canal "pago en línea" nuevo. Esto evita reescribir todo
el flujo de aprobación manual (útil para QR físico/eventos con caja).

Flujo elegido (online, vía Libélula):
  1. Usuario crea la Compra eligiendo "pagar en línea".
  2. Backend llama a REGISTRAR DEUDA con appkey + email + identificador
     de la Compra (compraId) + líneas_detalle_deuda (una línea por
     categoría/entrada) + callback_url apuntando al webhook propio +
     url_retorno apuntando al frontend (pantalla "gracias por tu
     compra").
  3. Se guarda id_transaccion (de Libélula) y url_pasarela_pagos en la
     Compra, estado sigue "pendiente".
  4. Se redirige/muestra al usuario la url_pasarela_pagos.
  5. Libélula hace GET a nuestro webhook cuando el pago se confirma
     (PAGO EXITOSO) — puede ser inmediato o en background según canal
     (Tigo/BNB tardan más).
  6. El webhook ejecuta la misma lógica que hoy hace
     ComprasService.aprobar() (crear usuarios, numerar entradas, QR,
     marcar confirmado, mandar correo) — sin intervención de Admin.
  7. Cron de reconciliación diaria llama a CONSULTAR PAGOS (o
     CONSULTAR DEUDAS POR FECHAS) para detectar pagos que el webhook
     no haya confirmado (falla de red, etc.) y cerrarlos igual.

3. NUEVO MÓDULO: pagos (Libélula)
-------------------------------------------------------------------
backend/src/modules/pagos/
  - libelula.service.ts
      registrarDeuda(compra): POST /rest/deuda/registrar
      consultarPagos(fechaInicial, fechaFinal): reconciliación
      consultarDeudaPorIdentificador(compraId)
      anularPago(...) / regenerarFactura(...)  [fase 2, opcional]
      Usa HttpModule (@nestjs/axios) o fetch nativo; timeout + 1 retry.
  - pagos.controller.ts
      @Publico()
      GET/POST /pagos/libelula/callback   ->  webhook "PAGO EXITOSO"
        - Verifica transaction_id contra Compra.libelulaIdTransaccion.
        - Idempotente: si la Compra ya está "confirmado", responde 200
          sin repetir el trabajo (Libélula puede reintentar el callback).
        - Delega en ComprasService (método extraído, ver sección 4).
  - pagos.module.ts

Seguridad del webhook (Libélula NO firma sus callbacks con HMAC según
la guía, solo manda transaction_id por querystring):
  - Mitigar spoofing verificando que transaction_id exista y coincida
    con una Compra en estado "pendiente" con metodoPago=LIBELULA.
  - Como confirmación fuerte, tras recibir el callback, el backend
    SIEMPRE hace una llamada de vuelta a CONSULTAR DEUDAS POR
    IDENTIFICADOR (server-to-server, con el appkey) para verificar
    pagado=true antes de confirmar la Compra. Así un callback falso
    no puede confirmar una compra no pagada.
  - Rate-limit del endpoint público (ya existe throttler global, si
    no, agregar uno específico).

4. REFACTOR MÍNIMO EN ComprasService
-------------------------------------------------------------------
- Extraer de aprobar() la parte "crear usuarios + numerar entradas +
  asignar QR + marcar confirmado + mandar correos" a un método privado
  reutilizable, ej. `confirmarCompra(compra, resueltoPorId?: string)`.
  - aprobar() (Admin) la llama con resueltoPorId = admin.id.
  - El nuevo flujo de Libélula la llama con resueltoPorId = null
    (o un id de "sistema"), marcando en auditoría que fue automático.
- crear(): agregar branch por metodoPago:
  - MANUAL: comportamiento actual (comprobante).
  - LIBELULA: no exige comprobante; al final de la transacción llama a
    LibelulaService.registrarDeuda(compra) y persiste los campos de
    la sección 2. Si falla el registro de deuda en Libélula, la Compra
    se crea igual en "pendiente" pero se informa el error al frontend
    para reintentar (no bloquear el cupo ya reservado, o revertir el
    cupo si se prefiere abortar — decidir con el usuario/negocio).

6. VARIABLES DE ENTORNO NUEVAS (env.validation.ts)
-------------------------------------------------------------------
LIBELULA_APPKEY          string, requerido cuando se habilite el canal
LIBELULA_API_URL         string, default "https://api.libelula.bo"
LIBELULA_CALLBACK_URL    string (URL pública del webhook propio,
                         ej. https://api.qpass.bo/pagos/libelula/callback)
LIBELULA_URL_RETORNO     string (URL del frontend post-pago)
SMTP_FROM                string, ej. "QPass <no-responder@qpass.bo>"
SMTP_SECURE              boolean, default false (true si puerto 465)

Nota: para pruebas, Libélula indica apuntar a producción con la
"llave de pruebas" que ellos asignen (no hay sandbox separado) — o
sea LIBELULA_APPKEY de test y de prod son ambas contra
api.libelula.bo, solo cambia el appkey.
